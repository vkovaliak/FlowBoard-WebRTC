- (decision) Stakes calibration: professional-grade rigor (portfolio piece, demoed to mentor/others) but practically scoped — no compliance/monetization/multi-team overhead.
- (decision) Product: FlowBoard Video Calls — Blazor Server (.NET10) app for P2P group video calls with screen sharing; practice project for WebRTC/real-time comms.
- (decision) Architecture: WebRTC mesh (full P2P between all participants), target group size ~4-5, no SFU/media server, self-contained single Blazor Server project.
- (decision) Signaling via built-in SignalR CallHub in same project; STUN only (Google public STUN stun:stun.l.google.com:19302); not connected to any other backend.
- (decision) Core scope: create/join room by room ID, multi-participant video+audio, screen share, call controls (mute/camera/screen-share/hang up), adaptive grid layout.
- (assumption) No additional source inputs (no design sketches, no reference app) — PRD built entirely from user's brain dump.
- (decision) Identity: participants set a display name before joining (shown under video tile); no accounts.
- (decision) Room join model: arbitrary user-typed room ID; nonexistent ID creates room, existing ID joins it; plus a 'generate random room ID' button. Rooms are ephemeral/in-memory, cease to exist when empty.
- (decision) No participant cap anywhere in code/config — unbounded room size. Mesh's practical performance ceiling is documented as an inherent technology characteristic, not an enforced limit.
- (decision) STUN-only, no TURN in v1: a failed peer pair fails independently with a subtle UI indicator; rest of call continues. TURN explicitly out of scope.
- (decision) Reconnection: manual rejoin only in v1; automatic reconnection out of scope.
- (assumption) Screen share concurrency: chose 'block' (disable share button for others while one participant is sharing) over 'replace', as the simpler implementation — user approved either, marked ASSUMPTION.
- (decision) Platform: desktop Chrome/Edge/Firefox only, mobile out of scope. Deployment: localhost is the primary v1 target; Azure deployment is a nice-to-have, not a blocker.
- (decision) Non-goals v1: chat, recording, auth/accounts, virtual backgrounds, persistent call history, TURN, mobile, automatic reconnection.
- (decision) Success bar: reliable happy-path demo for a dynamic/unrestricted number of participants (camera, audio, screen share, all controls, adaptive grid) plus clean, well-structured code that impresses the mentor.
