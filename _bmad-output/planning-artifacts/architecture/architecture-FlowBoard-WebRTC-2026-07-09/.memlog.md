- (decision) AD-1 Paradigm: Signaling-plane/Media-plane separation. C# (Blazor+SignalR) owns signaling relay + UI state only; JS owns all WebRTC objects (RTCPeerConnection, MediaStream) exclusively. C# never receives/holds a WebRTC object reference -- only opaque SDP/ICE strings cross the interop boundary. Blazor UI state (participant list, mute/camera flags) populated only via JS-to-C# callback events.
- (decision) AD-2 Deterministic offerer rule: the newly JOINING participant always initiates the SDP offer to each existing participant; existing participants only ever answer. Eliminates glare structurally -- no pair can ever have both sides simultaneously offering.
- (decision) AD-3 CallHub is an opaque relay: SendOffer/SendAnswer/SendIceCandidate forward payload verbatim to Clients.Client(targetConnectionId) (never broadcast to group), never parse/inspect SDP content server-side.
- (decision) AD-4 RoomRegistry (singleton service) is the single source of truth for room membership: nested ConcurrentDictionary<roomId, ConcurrentDictionary<connectionId, ParticipantInfo>> plus reverse ConcurrentDictionary<connectionId, roomId> for O(1) disconnect lookup. All mutation happens only inside CallHub methods; OnDisconnectedAsync handles teardown+notify.
- (decision) AD-5 No participant cap anywhere in JoinRoom or RoomRegistry -- explicit invariant to prevent a MaxParticipants config/constant creeping in later (PRD FR-9).
- (decision) AD-6 Local media is ONE shared MediaStream per session from a single getUserMedia() call, tracks fanned out via addTrack to every RTCPeerConnection. Mute/camera-off toggles operate on the shared tracks (track.enabled=false), not per-connection -- prevents redundant getUserMedia calls and desynced mute state.
- (decision) AD-7 Screen share is an ADDITIVE second video track via addTrack (triggers renegotiation), never replaceTrack against the camera -- required so camera thumbnails stay visible during a share per EXPERIENCE.md's screen-share-priority layout (UX spec requires sharer's own camera view too). Single-active-sharer enforced at UI layer only (Share Screen button disabled for others per PRD FR-12) -- CallHub has no track visibility to enforce it server-side (per AD-1).
- (decision) AD-8 Per-pair connection lifecycle is fully independent: JS tracks RTCPeerConnections in a Map<connectionId, RTCPeerConnection>; every lifecycle op (create/close/failure) touches exactly one Map entry, never iterates/mutates others. Structurally guarantees PRD FR-10 (per-pair failure isolation) and FR-8 (dynamic join/leave without disruption).
- (decision) JS owns the SignalR connection directly (JS SignalR client talks to /callHub), NOT routed through C#/JSInterop/IHubContext. Rationale: CallHub only ever does signaling relay + membership, none of which needs Blazor component state; routing every ICE candidate through Blazor's circuit would add a needless hop and couple signaling latency to Blazor's render thread. C# is informed of state changes (join/leave/mute/connection-issue) via JS-to-C# callbacks (DotNetObjectReference/[JSInvokable]) purely for UI rendering.
- (decision) STUN config: appsettings 'WebRtc' section bound to WebRtcOptions via IOptions<WebRtcOptions>; C# passes the ICE server list to JS as a parameter of the initializeCall() interop call at session start -- never hardcoded in any .js file.
- (decision) Project structure: /Components (Razor: RoomEntry, CallView, VideoTile, ControlBar, ScreenShareLayout), /Hubs (CallHub.cs), /Services (RoomRegistry.cs), /Models (DTOs: ParticipantDto, SignalPayload types), /Configuration (WebRtcOptions.cs), /wwwroot/js (webrtc-mesh.js as ES module: connection management + signaling client; media.js: getUserMedia/getDisplayMedia + track management; interop.js: DotNetObjectReference callback registration).
- (decision) CallHub method signatures: Task<List<ParticipantDto>> JoinRoom(string roomId, string displayName); Task SendOffer(string targetConnectionId, string sdp); Task SendAnswer(string targetConnectionId, string sdp); Task SendIceCandidate(string targetConnectionId, string candidateJson); Task SetMuteState(bool isMuted); Task SetCameraState(bool isCameraOn); override Task OnDisconnectedAsync(Exception? ex). Client callbacks (Clients.Caller / Clients.Client(id) / Clients.OthersInGroup): ReceiveOffer(callerConnectionId, sdp); ReceiveAnswer(callerConnectionId, sdp); ReceiveIceCandidate(callerConnectionId, candidateJson); ParticipantJoined(ParticipantDto); ParticipantLeft(connectionId); ParticipantMuteChanged(connectionId, isMuted).
- (decision) connectionId (Context.ConnectionId / HubConnection's own id) is the canonical peer identifier end-to-end -- never re-keyed to a custom participant GUID. Convention, not just a detail: keeps JS Map keys, C# dictionary keys, and DTOs all aligned on one identifier space.
- (assumption) [ASSUMPTION] Room deletion on empty is a soft/lazy invariant: RoomRegistry removes a room's inner dictionary when the last participant's disconnect leaves it empty; a benign micro-race (checking emptiness right as another join lands) is accepted rather than adding a per-room lock, since a stale-empty room dict causes no correctness issue (next join just repopulates it). Not discussed with user; flagged for review.
- (assumption) [ASSUMPTION] JS interop failure handling (e.g. JS throws during initializeCall) is not specified by PRD/UX -- this spine defers the exact error-surfacing UX to story-level detail, but the invariant (AD-1) still holds: any such error surfaces to C# via the OnLocalMediaError callback path, never a silent JS-side failure.
- (question) Open: exact renegotiation handling when addTrack triggers onnegotiationneeded mid-call (screen share start) -- does the SAME offerer-is-joiner rule apply, or does the track-adder always renegotiate-offers regardless of original join order? Architecture defers to: whoever calls addTrack (the sharer) initiates the renegotiation offer for that connection, symmetric with AD-2's spirit (state-changer offers) but distinct from AD-2's join-time rule. Logged as a distinct micro-rule, not a new AD, since it's a direct corollary.
- (decision) Renegotiation corollary of AD-2/AD-7: for screen-share start/stop (or any mid-call track add/remove), the participant whose track set changed (the sharer) is always the renegotiation offerer on every affected RTCPeerConnection; the counterpart always answers. Keeps the 'state-changer offers' rule consistent end-to-end.
