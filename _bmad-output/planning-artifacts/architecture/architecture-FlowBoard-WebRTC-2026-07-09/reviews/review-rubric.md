# Architecture Spine Review — FlowBoard Video Calls

## Overall verdict

This is a well-structured, portfolio-appropriate spine: the eight ADs fix most of the real divergence points a mesh WebRTC app needs (deterministic offerer, opaque relay, single membership source of truth, per-pair isolation, additive screen share), all five PRD §4 capabilities are mapped, and the named tech (`.NET 10` LTS, SignalR 10.x, `@microsoft/signalr` ^10, Google STUN) checks out as current. However, all four mermaid diagrams fail to parse as written — verified by running them through the actual mermaid v11 parser — and two real divergence points (a join-order race under AD-2, and how peers distinguish a camera track from a screen-share track) are left open where they should have been closed by a rule.

## Checklist judgments
- Divergence coverage — thin
- AD enforceability — adequate
- Deferred appropriateness — adequate
- Tech currency — strong
- PRD capability coverage — strong
- Dimension completeness (incl. operational envelope) — adequate
- Diagram validity — broken

## Findings

- **critical** All four mermaid diagrams fail to parse. Verified programmatically (mermaid v11.6.2, Node/jsdom, `mermaid.parse()`) against every diagram in the spine, plus minimal repros to isolate root cause. Two systematic bugs: (1) the Design Paradigm flowchart's two subgraph titles contain a bare `--` — `subgraph Signaling Plane -- C# / Blazor Server` (line 33) and `subgraph Media Plane -- Browser JS, per client` (line 40) — which mermaid's flowchart grammar tokenizes as the start of an edge-link (`EDGE_TEXT`), not literal text, so parsing fails immediately after `Server`/`client`. Repro confirms `subgraph SP["Signaling Plane -- C# / Blazor Server"]` (bracketed) parses fine. (2) All three sequence diagrams use `;` inside message text as an "and then" shorthand — e.g. line 178 `createPeerConnection(B.id); addTrack(local stream)`, line 179 `createOffer(); setLocalDescription`, line 185 `setRemoteDescription(offer); createAnswer(); setLocalDescription`, line 217/223 `createPeerConnection(...); offer`, line 246 `createOffer(); setLocalDescription`, line 256 `screenTrack.stop(); removeTrack(screenTrack) per connection`. Mermaid's sequence grammar treats `;` as a statement terminator equivalent to newline, so each of these becomes an orphan fragment with no actor/arrow and the parse fails. Repro confirms removing the semicolon parses fine. Content-wise, once the syntax is fixed, the diagrams *do* correctly depict AD-2 (joiner-always-offers, both 2-participant and 3rd-join diagrams), AD-8 (A<->B's connection explicitly untouched when C joins), and the renegotiation corollary (sharer offers on screen-share start/stop). *Fix:* bracket every subgraph title (`subgraph SP["Signaling Plane — C# / Blazor Server"]`) and replace every in-message `;` with a comma, "then", or em dash.
- **high** AD-2 doesn't close the concurrent-join race. `RoomRegistry` is a `ConcurrentDictionary` (AD-4), which guarantees thread-safety per individual operation but not atomicity across "add self" + "snapshot existing participants" as a compound step. If two participants call `JoinRoom` for the same room at nearly the same instant, each can compute an empty/stale existing-participants list before seeing the other, and — because AD-2 only fires the offerer role off that snapshot — neither ever offers to the other. The pair silently never connects, breaking full-mesh (PRD FR-5) with no error surfaced anywhere, which is exactly the class of divergence AD-2 exists to prevent (location: AD-2, AD-4). *Fix:* add an explicit rule that the add-to-registry + snapshot-read + `ParticipantJoined` broadcast for a given room execute as one serialized step (e.g. per-room lock), so concurrent joins can't race on "who's already here."
- **high** No rule specifies how a peer identifies which of a sender's (now two) video tracks is the screen-share track once received via `ontrack`. FR-21 (screen-share-priority layout), FR-12 (disable Share control for others), and FR-13 (revert layout when sharing stops) all depend on this distinction, but AD-7 only specifies the *sending* side (`addTrack`, never `replaceTrack`) and is silent on how the *receiving* side tells camera from screen (track order, `track.label`/kind heuristics, or a dedicated signaling event). Two independently-built stories on this could pick incompatible mechanisms (location: AD-7, Renegotiation corollary). *Fix:* extend AD-7 (or add a rule) specifying how the screen-share track is tagged/identified across the wire.
- **medium** FR-12's single-active-share is enforced UI-only by design (AD-7 explicitly notes "`CallHub` has no track visibility to enforce it server-side"), but no rule addresses the race window where two participants click Share Screen before either has received the other's start notification — both could renegotiate a screen track concurrently, producing two simultaneous shares, which directly violates the Glossary's "only one Participant's Screen Share can be active... at a time." The PRD's FR-12 assumption (block, not replace) implies this risk was accepted for simplicity, but the spine doesn't say so explicitly (location: AD-7). *Fix:* either state the race is accepted (add to Deferred with rationale, matching the FR-12 assumption) or specify a tie-breaker.
- **low** "Room-emptiness race on deletion" under Deferred reads as an already-made decision with a stated rule (remove-on-empty, race accepted, no lock) rather than something still open — it fits the shape of an `[ASSUMPTION]`-flagged AD more than a Deferred item, which the checklist treats as "not yet decided." Content is fine; only the classification is off (location: Deferred, bullet 6).

## Mechanical notes

- Tech currency check via web search: `.NET 10` GA'd 2025-11-11 as an LTS release supported to 2028-11-10 — matches the Stack table exactly. SignalR 10.x / `@microsoft/signalr` ^10.0.0 pairing is consistent with that. No evidence of Google's public STUN server (`stun:stun.l.google.com:19302`) being deprecated or shut down as of this review; it remains widely used, though it has always been unofficial/no-SLA — a risk the PRD already accepts explicitly (no TURN, v1 non-goal), so not a fresh architecture-level finding.
- Capability -> Architecture Map covers all five PRD §4 features (4.1 Room creation/joining through 4.5 Adaptive Grid) with plausible AD ownership; no PRD capability found unmapped.
- Diagram parsing was verified directly (not inferred) using `mermaid@11.6.2` under Node 24 + jsdom, with minimal isolated repros confirming both root causes before attributing them to the spine's actual diagram text.
