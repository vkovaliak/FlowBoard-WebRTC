# Adversarial Incompatibility Review — FlowBoard Video Calls

## Overall verdict

The spine's ADs are individually well-formed but describe single-actor, single-timeline behavior; none of them constrain the *composite* outcome when two compliant runtime instances (two joiners, two devs' cleanup paths, join-vs-share timing) execute concurrently. The sharpest hole is that AD-2's determinism depends on an atomicity guarantee AD-4 never actually promises, which produces a genuine glare condition under near-simultaneous joins.

## Findings

- **critical** Two participants, A and B, click "Join" within the same tens-of-milliseconds window. `CallHub.JoinRoom` for each executes concurrently on the server. Each compliant implementation does `RoomRegistry.Add(room, self)` → `snapshot = GetParticipants(room) excluding self` → `return snapshot` → `notify snapshot of self joining`. `ConcurrentDictionary` guarantees each individual op is thread-safe, but the four-step sequence is not atomic as a whole. If thread A's `Add` interleaves before thread B's snapshot read (and vice versa), **both** A and B compute the other as "already in room" and both, per AD-2's literal text ("the newly joining participant is always the offerer to every participant already in the room"), legitimately conclude *they* are the joiner relative to the other. Both create and send an offer to the other simultaneously — classic SDP glare (`setRemoteDescription` fails or is applied out of order against a connection already in `have-local-offer` state), producing either a stuck/duplicate connection or a silently dropped tile for that pair. Both implementations are letter-perfect against AD-2 and AD-4 as written. (AD-2, AD-4). *Fix:* Add an AD requiring `RoomRegistry` to expose a single atomic `AddAndSnapshot(roomId, connectionId, info)` operation (internally lock-per-room or use an actor/queue), and mandate that `JoinRoom` never calls `Add` and `GetParticipants` as separate steps. The "who is already in the room" snapshot and the membership write must be one indivisible operation, and offer-side tie-breaking (e.g., lexicographic connectionId compare) should be specified as a fallback for the case where both sides simultaneously believe they're the joiner.

- **high** `RoomRegistry` (AD-4) is described as one nested `ConcurrentDictionary` plus a reverse `connectionId -> roomId` dictionary "for O(1) disconnect lookup," but AD-4 never specifies write ordering/atomicity between the two structures. Developer 1 implements `JoinRoom`'s registry write as `rooms[roomId].TryAdd(connId, info)` *then* `reverseLookup.TryAdd(connId, roomId)` — a reasonable, AD-4-compliant reading. Developer 2 implements `OnDisconnectedAsync` (the mandated "sole teardown path") as `reverseLookup.TryRemove(connId, out roomId)` *then* remove from `rooms[roomId]` — also AD-4-compliant, and it must use the reverse map since that's the whole point of AD-4's O(1) clause. SignalR can invoke `OnDisconnectedAsync` for a connection concurrently with an in-flight hub method call on that same connection (a documented SignalR behavior, not a contrived edge case: transport-level disconnect detection is independent of the hub method dispatch queue). If disconnect fires in the gap between Dev 1's two writes, Dev 2's lookup misses (reverse map not yet populated), disconnect cleanup no-ops, and the participant row in `rooms[roomId]` is permanently orphaned — a ghost `ParticipantInfo` that every future `GetParticipants` snapshot includes, that every future joiner will dutifully try to offer to (AD-2), silently failing at `Clients.Client(deadId)` per AD-3's "verbatim forward, never inspect" rule with no error surfaced. (AD-3, AD-4). *Fix:* Tighten AD-4 to mandate the two dictionaries are written/removed as a single critical section (e.g. a per-connectionId lock, or collapse to one dictionary keyed by connectionId whose value carries roomId, eliminating the two-writer race entirely), and require `OnDisconnectedAsync` to be idempotent/safe against concurrent in-flight `JoinRoom` for the same connectionId.

- **high** AD-2/AD-8 (join-time connection creation: "createPeerConnection(peerId); addTrack(local stream)") and AD-7 (screen-share: "addTrack(screenTrack) ... on every *existing* RTCPeerConnection") are each unambiguous in isolation but disagree on what happens for a connection created *between* the two events. Scenario: participant F is already screen-sharing. Participant D joins and, per AD-2, is the offerer to every participant already in the room, including F — but per AD-2's own rule, F (being the existing/answerer side) never initiates a connection to D; F only creates its `RTCPeerConnection(D)` reactively when D's offer arrives. A developer building the AD-7 screen-share path, reading "every existing RTCPeerConnection" literally, only iterates F's Map *at the moment `getDisplayMedia()` resolves* — D's not-yet-created connection is correctly out of scope for that loop, by design. A different developer building the AD-2/AD-8 connection-creation path, reading AD-6 literally ("`getUserMedia()`... tracks... added via `addTrack()` to every `RTCPeerConnection` created in that session"), only adds the *camera/mic* stream to newly created connections — AD-6 says nothing about an active screen-share track. Composed: D's connection to F is created with camera+mic only; nobody's code path ever adds F's active screen track to that specific connection, because it falls in the seam between "existing connections get retrofitted" (AD-7) and "new connections get the AD-6 stream" (AD-6/AD-2). D never sees F's share unless F stops and restarts sharing. Both implementations are individually correct against their AD's literal text. (AD-2, AD-6, AD-7, AD-8, Renegotiation corollary). *Fix:* Add a clause (or extend AD-7) requiring that `createPeerConnection()` always adds **all currently-active local tracks** — the AD-6 camera/mic stream *and* any active screen-share track — not just "the local stream," so newly created connections converge to the same state regardless of join-vs-share ordering.

- **high** AD-4 mandates `OnDisconnectedAsync` as the sole teardown path, but SignalR's transport-level disconnect detection has non-trivial latency (default keep-alive/timeout on the order of tens of seconds) unless the client explicitly closes the connection first. Developer 1 builds the "join / rejoin" flow (`RoomEntry` → `CallView`): on every page load (including a hard refresh), it opens a fresh JS SignalR client connection and calls `JoinRoom` — fast, typically sub-second. Developer 2 builds no explicit `beforeunload`/`pagehide` handler to proactively stop the old hub connection on refresh, reasoning (correctly, per AD-4's text) that "OnDisconnectedAsync is the sole teardown path" and the browser will eventually trigger it — which it does, but only after the timeout elapses. Composed: on a refresh, the same human is registered in `RoomRegistry` under **two** connectionIds simultaneously for the timeout window — the stale one (about to time out) and the fresh one (just joined). Every other participant receives a `ParticipantJoined` for the new id while the old id's ghost tile remains rendered and undead in their roster (populated by mirrored `[JSInvokable]` callbacks per AD-1) until the old connection finally times out — a duplicate video tile, and per AD-2 every other existing participant is not required to offer (only the joiner offers), so the ghost tile shows as permanently "connecting" until cleanup. Neither implementation violates AD-4's text. (AD-1, AD-4, AD-6 session-boundary ambiguity). *Fix:* Add an AD defining "session identity" independent of transport connectionId (e.g., a client-generated stable participant token surviving refresh) so a refreshing client can proactively signal "this replaces connectionId X" — or mandate an explicit `beforeunload` hook that synchronously requests hub disconnect before navigation, closing the timeout window instead of relying on passive detection.

- **medium** AD-8's rule text — "every lifecycle operation (create, close, ICE-failure handling, renegotiation) acts on exactly one Map entry" — governs *isolation between pairs* but never explicitly requires that removing a Map entry be paired with `pc.close()`. Developer 1, handling the `OnParticipantLeft` callback (fired when `RoomRegistry`/AD-4 removes someone), writes `pc.close(); connections.delete(id)`. Developer 2, handling the same callback for a different code path (e.g. an ICE-failure-triggered removal under the same AD-8 clause), writes only `connections.delete(id)`, reasoning that once nothing references the `RTCPeerConnection` it will be GC'd — both are "acts on exactly one Map entry" compliant. The un-closed connection keeps its underlying transport, tracks, and (if it's the far end of a still-successfully-connected ICE session) bandwidth alive indefinitely — the browser tab's camera/mic indicator or network activity for a "left" peer lingers, and if any other component still holds a reference to that `RTCPeerConnection` (e.g., a `VideoTile` bound to its remote stream), the tile can freeze on a stale last frame instead of disappearing. Combined with the ghost-registry findings above, this yields the three-way disagreement the review was asked to probe: `RoomRegistry` (server) says gone, the Blazor-side mirrored roster (built from AD-1 callbacks) says gone, but the JS `Map`/underlying `RTCPeerConnection` says still-alive-and-transmitting. (AD-1, AD-4, AD-8). *Fix:* Tighten AD-8 to explicitly require `pc.close()` (and stopping any locally-added remote-stream references) as an atomic, mandatory pair with Map-entry removal on every removal path — never delete-without-close, never close-without-delete.
