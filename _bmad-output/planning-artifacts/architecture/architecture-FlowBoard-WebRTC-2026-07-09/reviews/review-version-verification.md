# Version Verification Review — FlowBoard Video Calls

## Overall verdict

Every named technology/API in the spine checks out against current sources as of 2026-07-09: .NET 10 is genuinely the current LTS, `@microsoft/signalr ^10.0.0` is real and matches ASP.NET Core 10, the WebRTC APIs cited (`addTrack`/`removeTrack`→`onnegotiationneeded`, `getDisplayMedia`) are current and not deprecated, and `DotNetObjectReference`/`[JSInvokable]` remains Microsoft's documented pattern for .NET 10. One numeric detail (the `.NET 10` end-of-support date) is off by four days, and the Google STUN dependency, while functionally correct today, is asserted with a confidence the record doesn't fully support.

## Findings

- **low** `.NET / ASP.NET Core (Blazor Server) | 10 (LTS, GA 2025-11-11, supported to 2028-11-10)` (Stack table, line 120). GA date (2025-11-11) is correct. The end-of-support date is stated as **2028-11-10**, but Microsoft's official support policy page (dotnet.microsoft.com/platform/support/policy/dotnet-core) and endoflife.date both list **2028-11-14** (3 years from GA, matching .NET's Tuesday-release-day convention). *Fix:* correct the table to `supported to 2028-11-14`, or cite the source if a different figure was intentionally used.

- **low** `STUN | Google public STUN, stun:stun.l.google.com:19302 [ADOPTED]` (Stack table, line 123). The host/port is real and in wide current use, and no web-search evidence surfaced of an official Google deprecation as of 2026-07-09 — so the claim itself is not wrong. However, it's a free, no-SLA, no-contract third-party service (Google has never published an availability guarantee for it, and community reports of intermittent throttling/blocking exist), which is a materially different risk profile than a version number being current. The spine's Deferred section already accepts "STUN-only, no TURN, calls fail if STUN is unreachable" as a conscious tradeoff, which mitigates this, but the `[ADOPTED]` tag reads as more verified/durable than the underlying research supports. *Fix:* either add a one-line note in Deferred/Stack acknowledging "no SLA, verify reachability at deploy time" or leave as-is since the risk is already covered by AD-8/PRD FR-10 — no architectural change needed, just tone down the certainty implied by `[ADOPTED]`.

- **informational** `@microsoft/signalr (JS client) | ^10.0.0` (Stack table, line 122). Confirmed current and correct — matches ASP.NET Core 10 server-side SignalR. Note for awareness only: there was a short window (reported 2025-11-14, dotnet/aspnetcore#64367) where the 10.0.0 npm package lagged its NuGet counterpart; that gap is now resolved (issue closed/fixed), so no action needed, but worth knowing if a story ever pins an exact patch version and npm briefly 404s again post-release.

- **none** RTCPeerConnection `addTrack()`/`removeTrack()` → `onnegotiationneeded`, `getDisplayMedia()`, `RTCSessionDescriptionInit`/`RTCIceCandidateInit`, `DotNetObjectReference`/`[JSInvokable]`, and `ConcurrentDictionary` all verified as current, non-deprecated, and correctly used against their documented behavior (MDN, W3C Screen Capture spec, and Microsoft Learn aspnetcore-10.0 docs). No fix needed.
